# Admin-уведомления в Telegram — дизайн

## Повод

Владелец лиги (админ) сейчас не видит, что происходит в сервисе, кроме как заходя вручную в
Админку или дашборд Supabase. Нужны Telegram-уведомления в личку админу о трёх событиях:
новая регистрация участника, новый прогноз (в т.ч. от GridBot), результат гонки занесён в
систему. Не общая автоматическая сводка (её польза для владельца низкая — это внутренняя кухня
крона), а именно продуктовые события.

Ключевые решения из брейншторма:
- Уведомления идут в личный чат админа с ботом (`che_f1_predict_bot`) — тот же чат, что уже
  использовался для смоука Task 1 плана Telegram Mini App.
- **Событийно, не polling.** Владелец явно отверг вариант «дёргать GitHub Actions каждые
  N минут круглый год ради редких событий» — между гонками бывают паузы по 2 месяца, при
  polling это сотни бесполезных запусков. Вместо этого — Postgres-триггеры на изменение данных
  + асинхронный HTTP прямо из базы (`pg_net`), без опроса.
- **Тихие часы 22:00–10:00 МСК** — ночью уведомления не шлются сразу, а копятся; один раз в день
  (10:05 МСК) уходит «разгрузка» накопленного. Никакого крона каждые полчаса — то, ради чего
  вообще пересматривали дизайн.
- Форматирование текста сообщений и решение «слать сейчас / положить в очередь» — в
  TypeScript-Edge Function (как `telegram-auth`, уже есть опыт и тестовая дисциплина в проекте),
  а не в PL/pgSQL — легче покрыть тестами, легче читать.

## Архитектура

```
INSERT users / INSERT predictions / INSERT|UPDATE results   (событие в БД)
  → Postgres-триггер (тонкий, миграция) → net.http_post()  (асинхронно, не блокирует запись)
      → Edge Function `admin-notify`
          строит текст события → проверяет час в Europe/Moscow
            10:00–22:00 → сразу sendMessage в Telegram (личка админа)
            иначе       → INSERT текста в admin_notification_queue

Раз в день, 10:05 МСК (новый крон-пункт в существующем telegram-notify.yml):
  scripts/telegram/notify.js adminflush
    → SELECT * FROM admin_notification_queue ORDER BY created_at
    → sendTelegram(text) на каждую строку
    → DELETE обработанных строк
```

Разгрузка очереди — не через Edge Function, а обычным cron-режимом `notify.js` (та же схема, что
`results()`/`deadline()`): читает БД напрямую, шлёт через уже существующий `sendTelegram()`. Нет
причин заводить лишний HTTP-прыжок туда, где и так есть прямой доступ к БД раз в сутки.

### Таблица `admin_notification_queue`

```sql
create table public.admin_notification_queue (
  id bigint generated always as identity primary key,
  text text not null,
  created_at timestamptz not null default now()
);
alter table public.admin_notification_queue enable row level security;  -- без политик: только service-role
```

### Триггеры

`create extension pg_net;` (сейчас не включено, `supabase_vault` — уже включено, для токена
бота). Одна тонкая PL/pgSQL-функция `notify_admin_event(event_type text, payload jsonb)`,
вызывается тремя триггерами:
- `AFTER INSERT ON public.users` → `{event_type: 'registration', display_name, telegram_username}`
- `AFTER INSERT ON public.predictions` → `{event_type: 'prediction', user_id, race_id}`
  (срабатывает одинаково и на человека, и на GridBot — это обычная строка в той же таблице, без
  special-case; повторные правки прогноза до дедлайна — `UPDATE`, не `INSERT`, уведомление шлётся
  только на первую постановку)
- `AFTER INSERT OR UPDATE ON public.results` → `{event_type: 'result', race_id}` (в таблице всегда
  upsert через `set_race_result()` — `ON CONFLICT DO UPDATE`, поэтому нужны оба события)

Функция только пакует поля в JSON и делает `net.http_post` на URL Edge Function — никакой
логики форматирования или тихих часов в SQL. Токен бота и chat_id самому триггеру не нужны —
их знает только Edge Function.

### Edge Function `admin-notify`

Принимает `{event_type, payload}`. По `event_type` достраивает текст (для `prediction`/`result`
дозапрашивает `display_name`/`race.name` через `supabaseAdmin`, т.к. в вебхуке пришли только id).
Читает токен бота из `supabase_vault`, chat_id админа — константа в коде функции (тот же класс
данных, что `BOT_USERNAME` в `notify.js`: не секрет, практически не меняется).

Проверяет текущий час в Europe/Moscow:
- 10:00–22:00 → `fetch` в `https://api.telegram.org/bot<token>/sendMessage` на chat_id админа.
- иначе → `supabaseAdmin.from('admin_notification_queue').insert({text})`.

Обе части (построение текста по `event_type`, граница «10:00–22:00») — чистые функции, без
побочных эффектов, тестируются как `verify.ts` из Task 4 ветки `telegram-mini-app`.

### Разгрузка очереди (`notify.js adminflush`)

Новый режим в `scripts/telegram/notify.js`, тот же паттерн, что существующие `raceweek`/
`deadline`/`results`: `q()` за строками очереди, `sendTelegram()` на каждую, `q()` на `DELETE`.
Новый крон-пункт в `telegram-notify.yml`: `5 7 * * *` (10:05 МСК, раз в день — не 24-48 раз).
В обычный день без ночных событий этот запуск не находит строк и ничего не шлёт.

## Тексты сообщений (примерно, финальная редакция — в реализации)

- `registration`: `🆕 Новый участник: <display_name>`
- `prediction`: `📝 <display_name> поставил прогноз на <race.name>`
- `result`: `🏁 Результат гонки <race.name> занесён в систему`

## Что НЕ меняется

`redeem_invite()`, `set_race_result()`, запись прогноза из `Predict.tsx` — ни одна из
существующих точек записи не трогается напрямую; уведомления полностью на стороне триггеров,
это чистая надстройка. Существующие каналы (общий чат лиги: напоминания, итоги гонок) не
затрагиваются — это отдельный получатель (личка админа), отдельный механизм.

## Разовая ручная настройка

- `create extension pg_net;` — накатывается миграцией, ручных действий не требует.
- Токен бота уже есть как секрет Edge Function (переиспользуется из `telegram-auth`, тот же
  `TELEGRAM_BOT_TOKEN`) — но для вызова из PL/pgSQL/`pg_net` вместо секретов Edge Function нужен
  URL самой функции `admin-notify` (доступен после первого деплоя, зашивается в миграцию с
  триггерами или хранится в `app_settings`, решить в плане реализации) и, при необходимости,
  service-role/anon ключ для авторизации вызова.
- Задеплоить `admin-notify` тем же способом, что `telegram-auth` (`supabase functions deploy
  admin-notify --use-api`).

## Тестирование

- Edge Function: юнит-тесты чистых функций (текст по `event_type`, граница тихих часов
  10:00/22:00 — включая пограничные случаи 09:59/10:00/21:59/22:00), TDD как `verify.ts`.
- `notify.js adminflush`: юнит-тест на пустую очередь (ничего не шлёт) и на несколько строк
  (шлёт все, потом чистит), в стиле существующего `notify.test.js`.
- Сквозной путь (триггер → `pg_net` → Edge Function → Telegram, и накопление в тихие часы) —
  ручной смоук после деплоя: тестовая регистрация/прогноз в дневное и (симулированное) ночное
  время, проверка что сообщение реально пришло или реально легло в очередь. Эмпирически, не на
  веру — `pg_net` в этом проекте раньше не использовался.

## Риски / открытые технические вопросы

- **`pg_net` раньше не использовался в проекте** — перед тем как закладывать в план как решённый
  вопрос, стоит эмпирически проверить на реальном free-tier проекте Supabase, что расширение
  ставится и `net.http_post` реально долетает до Edge Function (не полагаться, что «должно
  сработать»).
- **At-most-once доставка.** `pg_net` не делает ретраи — если Edge Function на момент вызова
  недоступна, конкретное уведомление теряется без сообщения об ошибке где-либо. Осознанно
  принятый риск для фичи уровня «для отслеживания», ретраи не строим (YAGNI).
- Как именно `pg_net`-триггер узнаёт URL Edge Function и получает право её вызвать (авторизация
  запроса) — механика уточняется на этапе плана реализации, не архитектурное решение.

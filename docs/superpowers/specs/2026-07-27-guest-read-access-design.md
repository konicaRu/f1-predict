# Гостевой read-only доступ без регистрации — дизайн

## Повод

Пользователь предложил: снять требование регистрации для тех, кто просто хочет посмотреть на
сервис (потенциальные новые игроки, друзья друзей), не давая им возможность делать прогнозы.
Изначальная идея — гостевой аккаунт с ручным одобрением админом, чтобы отсечь ботов-регистрации.
В обсуждении пришли к более простому решению: раз доступ read-only, регистрация гостю вообще не
нужна — открываем чтение конкретных данных анонимной роли (`anon`), проблема ботов-регистраций
снимается сама (регистрироваться по-прежнему может только реальный участник через инвайт-код).

Решили показывать **реальную лигу** (реальные имена, реальные прогнозы после дедлайна, реальный
зачёт), не отдельную демо-витрину с фейковыми данными — это было явное решение пользователя,
с пониманием, что приватность данных друзей при этом снижается (публично доступно любому в
интернете, не только замкнутому кругу лиги).

## Что видит гость

Read-only, без аккаунта:
- **Календарь** — список гонок, дедлайны, статусы.
- **Результаты** — реальный топ-10, разбивка прогнозов игроков и очков, drift-chart (то же, что
  видят между собой участники после дедлайна конкретной гонки).
- **Общий зачёт сезона** — реальные имена и очки.
- **Правила** — уже статический контент, просто снимаем гейт членства.

Гость НЕ видит: вкладку «Прогноз» (нечего делать без действия), «Админку», прогнозы до
дедлайна гонки (тот же гейт по времени, что и сейчас для участников), любые данные `users` кроме
`id`+`display_name` (без `telegram_username`/`telegram_user_id`).

## Архитектура доступа

Третий уровень поверх существующих двух (аноним=ничего, member=всё через `is_member()`):
**анонимное чтение подмножества данных**, реализовано ДОПОЛНИТЕЛЬНЫМИ RLS-политиками для роли
`anon` — существующие политики для `authenticated`/`is_member()` не трогаем вообще.

### Кил-свитч

Новая мини-таблица (один булевый флаг), функция `guest_access_enabled()` (SECURITY DEFINER, по
образцу `is_admin()`), которую проверяют все новые anon-политики. Переключатель — чекбокс в
Админке, дёргает функцию-сеттер с проверкой `is_admin()` (по образцу `set_race_result()`).
Выключатель на уровне БД — реально отзывает доступ у `anon`, а не просто прячет UI-кнопку.

### RLS / гранты (новые политики, `anon`)

| Таблица/view | Что открываем | Условие |
|---|---|---|
| `races` | `select` всех колонок | `guest_access_enabled()` |
| `drivers` | `select` всех колонок | `guest_access_enabled()` |
| `race_driver_pool` | `select` | `guest_access_enabled()` |
| `results` | `select` | `guest_access_enabled()` |
| `predictions` | `select` | `guest_access_enabled()` **и** `now() > races.deadline_utc` для гонки (тот же гейт по времени, что уже есть для `authenticated`) |
| `users` | `select` только колонок `id, display_name` | `guest_access_enabled()` |
| `scores` (view) | `select` | `guest_access_enabled()` — **требует эмпирической проверки**, как вьюха ведёт себя под `anon` (Postgres-вьюхи по умолчанию используют права владельца, не вызывающей роли; возможно потребуется `security_invoker` или отдельный grant) |

`invite_codes`, `result_changes`, любые admin-функции (`set_race_result`, `redeem_invite` и
т.п.) — анониму недоступны, как и сейчас. Ничего из существующих грантов/политик для
`authenticated` не меняется.

## Фронтенд

- Корень сайта (`/`) без сессии показывает гостевой вид (Календарь/Результаты/Зачёт/Правила) с
  заметной кнопкой «Войти», а не редиректит на `/login` как сейчас.
- Новые публичные маршруты (или существующие компоненты в read-only режиме без обёртки
  `ProtectedRoute`) для тех же четырёх страниц.
- Залогиненные участники — поведение не меняется, видят свой обычный защищённый вид.
- Вкладка «Прогноз»/«Админка» гостю не показываются в навигации вообще.

## Тестирование

По образцу существующих `scripts/db/*.test.js` (rolled-back транзакция):
1. При включённом свитче `anon` читает races/drivers/results/predictions-после-дедлайна/
   users(id,display_name)/scores — непустой результат.
2. При выключенном свитче `anon` получает 0 строк по всем перечисленным.
3. `anon` никогда не видит `predictions` до дедлайна гонки (даже при включённом свитче).
4. `anon` нигде не может писать (insert/update/delete) — ни в новых, ни в старых таблицах.
5. `anon` не видит `telegram_username`/`telegram_user_id` в `users`.
6. Существующие RLS-тесty для `authenticated`/`is_member()` остаются зелёными без изменений
   (регрессия — новые политики не должны задевать старые).

Плюс e2e-смоук в браузере: открыть сайт в приватном окне (без логина) → видно
Календарь/Результаты/Зачёт/Правила → нет доступа к Прогнозу/Админке → кнопка «Войти» работает.

## Риски

- Данные друзей (имена, точность прогнозов) становятся публичными для всего интернета — осознанно
  принятое решение пользователя, не техническая недоработка.
- У проекта уже был инцидент с эскалацией прав через `anon`-ключ (миграция `0013`, закрыт
  2026-07-22) — новые anon-политики проверять эмпирически в откатываемой транзакции перед
  применением к проду, не полагаться на то, что «должно сработать».
- Поведение view `scores` под `anon` — открытый технический вопрос, требует проверки до того, как
  писать план реализации как факт.

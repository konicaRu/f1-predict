# Telegram Mini App — голосование прямо в чате — дизайн

## Повод

Роадмап (`product-roadmap/ROADMAP.md`, раздел NOW) называет это первым пунктом: «Telegram:
голосование через Mini App (реюз текущего drag-and-drop UI внутри Telegram), доп. канал к
сайту, не замена». Сейчас бот только шлёт исходящие сообщения (напоминания, итоги) через Bot
API + GitHub Actions cron — входящих действий не принимает вообще.

Ключевые решения из брейншторма:
- Голосовать через Mini App сможет **кто угодно, включая тех, у кого ещё нет аккаунта в лиге** —
  инвайт-код вводится внутри Mini App, не требует захода на сайт.
- Аккаунт, созданный через Telegram, и аккаунт на сайте — **один и тот же** (единая сессия), не
  параллельная identity.
- Новый пользователь получает **анонимный Supabase-аккаунт** (без email/пароля) — email+пароль
  можно будет привязать тем же аккаунтом позже, но это отдельная фича, не часть этого дизайна.
- К напоминаниям о дедлайне в этой же фиче добавляется inline-кнопка, открывающая Mini App сразу
  на нужной гонке.

## Архитектура

Telegram Mini App — это **тот же сайт**, открытый внутри Telegram WebView, а не отдельное
приложение. Весь существующий UI (`Predict.tsx`, `PredictionSlots`/`DriverPool`, `Calendar`,
`Standings`/`Results`/`Rules`, RLS, `redeem_invite()`) используется **без единой правки** — вся
новая логика сосредоточена в одной точке входа: обмене подписанных Telegram-данных на настоящую
Supabase-сессию.

```
Telegram (WebView) → index.html (+ telegram-web-app.js) → AuthContext bootstrap
  → Edge Function `telegram-auth` (проверка initData, find-or-create аккаунт, mint сессия)
  → supabase.auth.setSession(...) → дальше ВСЁ как при обычном логине с сайта
```

### Edge Function `telegram-auth`

Единственный новый серверный компонент в проекте (до сих пор всё было cloud-direct: Postgres RPC
+ фронт, без отдельного бэкенда) — нужен, потому что проверка HMAC-подписи Telegram требует
секретного бот-токена на сервере, а выдача настоящей Supabase-сессии требует service-role ключ —
ни то, ни другое нельзя доверить клиенту или обычному Postgres RPC (RPC не может подписывать
Supabase JWT самостоятельно).

**Контракт:**
- Вход: `initData` (строка, как её отдаёт `window.Telegram.WebApp.initData`).
- Проверка: HMAC-SHA256 подписи `initData` бот-токеном (стандартная процедура валидации Telegram
  Web App, описана в их доке) + свежесть `auth_date` (отсекать старые/переигранные данные).
- Если подпись невалидна — 401, сессия не выдаётся, дальше фронт ведёт себя как неавторизованный
  визит (виден обычный `/login`).
- Если валидна — извлекается `telegram_user_id` + `first_name`/`username`:
  - Ищет `telegram_links` по `telegram_user_id`.
  - Нашла → минтит сессию для существующего `user_id`.
  - Не нашла → создаёт новый **анонимный** Supabase-аккаунт (Admin API, без email/пароля),
    пишет строку в `telegram_links`, минтит сессию для него.
  - Точный Admin API вызов для «выдать сессию под конкретный существующий `user_id` из
    привилегированного контекста» — уточняется в плане реализации (варианты: генерация и сразу
    серверная верификация magic-link без реальной отправки письма, либо другой поддерживаемый
    Admin-механизм) — архитектурно это не блокер, встроенный в Supabase Admin SDK путь есть.
- Выход: `{ access_token, refresh_token }` (или ошибка).

### `telegram_links` — таблица связи

```sql
create table public.telegram_links (
  telegram_user_id bigint primary key,
  user_id uuid not null references auth.users(id) on delete cascade,
  created_at timestamptz not null default now()
);
alter table public.telegram_links enable row level security;  -- без политик: только service-role (Edge Function)
```

Специально **отдельно от `public.users`**, а не переиспользует существующие колонки
`telegram_username`/`telegram_user_id` на `users` (они есть с самого начала, но не используются
нигде): связь Telegram↔аккаунт должна существовать ещё ДО того, как появляется строка в
`public.users` (та появляется только после `redeem_invite`, т.е. после ввода инвайт-кода) —
иначе повторное открытие Mini App человеком, который до конца не долистал онбординг, будет
распознаваться заново как новый пользователь.

## Сценарий

1. Юзер жмёт кнопку меню бота (или inline-кнопку из напоминания) → открывается Mini App.
2. `index.html` подключает официальный `telegram-web-app.js`. Если
   `window.Telegram.WebApp.initData` не пусто — фронт **на каждом открытии** (не только в первый
   раз) отправляет его в `telegram-auth` вместо обычной проверки сохранённой сессии. Небольшая
   избыточность для уже привязанных ради безопасности: не даёт перепутать пользователей на одном
   устройстве/чужом телефоне.
3. Функция проверяет подпись → ищет `telegram_links` → выдаёт сессию (существующую или новую).
4. Фронт делает `supabase.auth.setSession(...)`, дальше едет по обычным маршрутам без изменений:
   сессия есть, но `is_member()` = false (нет строки в `public.users`) → `ProtectedRoute` уводит
   на `/redeem`, ровно как у нового email-пользователя сегодня.
5. `/redeem` — существующий экран, единственная правка: поле имени предзаполняется
   именем/юзернеймом из Telegram (редактируемо), если приложение запущено внутри Mini App. Дальше
   штатный `redeem_invite()` RPC без изменений — display_name-коллизии обрабатываются уже
   существующей логикой (unique-констрейнт с миграции `0015`).
6. Уже привязанные участники — шаги 2-3 проходят молча за доли секунды, сразу видят
   Календарь/Прогноз.

**Ошибка проверки** (истёк `initData`, невалидная подпись) — сессия просто не выставляется,
приложение ведёт себя как обычный неавторизованный визит.

## Напоминания (`scripts/telegram/notify.js`)

Сообщение о дедлайне получает inline-кнопку `web_app`:
```js
reply_markup: { inline_keyboard: [[{ text: 'Поставить прогноз', web_app: { url: `${SITE_URL}/predict/${raceId}` } }]] }
```
Открывает Mini App сразу на нужной гонке — основной практический смысл всей фичи (не искать бота
и не переключаться в браузер, чтобы проголосовать).

## Что НЕ меняется

`Predict.tsx`, `PredictionSlots`/`DriverPool`, `Calendar`/`Standings`/`Results`/`Rules`,
`redeem_invite()` RPC, вся существующая RLS, `AuthContext`/`ProtectedRoute`/`AdminRoute` (кроме
точки bootstrap для Telegram-обмена). Гостевой read-only доступ (`/g/*`, отдельная недавно
влитая фича) тоже не затрагивается — разные механизмы для разных сценариев.

## Разовая ручная настройка (по образцу существующих `scripts/telegram/README.md`,
`scripts/export/README.md`)

- В Supabase Dashboard включить **Anonymous sign-ins** (Auth → Providers) — выключено по
  умолчанию.
- В BotFather настроить Menu Button / Web App URL бота на адрес сайта.
- Секреты Edge Function: `TELEGRAM_BOT_TOKEN` (уже есть, используется `scripts/telegram/`) —
  переиспользуется; service-role ключ Edge Function получает автоматически от Supabase, заводить
  вручную не нужно.

## Тестирование

- Postgres-слой (по образцу `scripts/db/*.test.js`, откатываемая транзакция): `telegram_links` —
  создание, поиск по `telegram_user_id`, RLS реально блокирует прямой доступ без service-role.
- Edge Function — unit-проверка HMAC-валидации на известных валидных/невалидных/просроченных
  `initData` (тестовые векторы можно сгенерировать локально тем же алгоритмом, зная тестовый
  бот-токен).
- Ручной e2e-смоук в Telegram (аналогично существующему смоуку бота): открыть Mini App без
  аккаунта → ввести инвайт-код → увидеть Календарь; закрыть и открыть снова → сразу залогинен;
  нажать кнопку из напоминания → попасть сразу на нужную гонку.

## Риски / открытые технические вопросы

- Точный Admin API вызов для минта сессии существующему `user_id` без email — нужно
  зафиксировать во время планирования/реализации (это API-механика, не архитектурное решение).
- Anonymous sign-ins — фича Supabase, которую проект раньше не использовал; убедиться, что она не
  открывает случайных анонимных сессий где-то ещё в приложении помимо явного пути через
  `telegram-auth` (RLS и так не даёт анонимной сессии ничего, кроме своей будущей `predictions`-
  строки после `redeem_invite`, но стоит явно перепроверить в тестах).
- Как и с гостевым доступом — HMAC-проверка должна быть проверена эмпирически (валидные/фейковые
  данные), не приниматься на веру, что «библиотечный пример сработает».

# Encrypted Users Recovery Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans, последовательно. Пользователь поручил сохранить пользователей в облаке и выполнить учебное восстановление.

**Goal:** Резервировать авторизацию вместе с игровыми данными и доказать восстановимость в изолированном PostgreSQL.

**Architecture:** pg_dump одной согласованной версии auth/public/extensions с исходными схемами и данными. AES-256-GCM шифрует dump и manifest; только ciphertext попадает в приватный `f1-predict-archive/full/`. На runner создаётся PostgreSQL-контейнер без сети, в новую пустую БД восстанавливается именно расшифрованный файл и сравниваются все таблицы и scores с экспортированным snapshot источника. Полезные файлы временно лежат только в RUNNER_TEMP; логов с содержимым строк нет.

**Tech Stack:** Node 22 crypto, pg, Docker, официальный закреплённый supabase/postgres:17.6.1.136 (рабочая база PostgreSQL 17.6), GitHub Actions.

## Ограничения

- Рабочая БД только читается; восстановление разрешено только в отдельный Docker-контейнер с `--network none`, без портов наружу.
- Не создавать платные Supabase-проекты/ветки. Не отправлять Telegram.
- Auth dump включает исходные UUID, password hashes, identities и связанные auth-таблицы. Пароли/ключи/дампы не выводить в логи и не публиковать как artifacts.
- Ключ восстановления: отдельный файл вне репозитория + зашифрованный GitHub Secret FULL_BACKUP_KEY. Ключ не коммитить даже в приватный архив.
- Платформенные Auth settings/API keys/SMTP/OAuth и развёртывание Edge Functions не восстанавливаются одним DB dump; инструкция фиксирует отдельные шаги.
- Сохранять версии; данные auth не добавлять в Google Sheets.

## Задачи и проверки

- [ ] Тесты шифрования: точный binary round-trip, неверный ключ, повреждённые ciphertext/tag, неверный формат.
- [ ] encrypted-backup.js: encryptBackup/decryptBackup с AES-256-GCM, случайным IV и аутентифицированной версией.
- [ ] full-backup.js: экспорт PostgreSQL snapshot, pg_dump, fingerprints таблиц и scores; без вывода строк.
- [ ] Изолированное восстановление, проверка fingerprints и UUID-связей, отчёт только со счётчиками/хешами.
- [ ] full-backup.yml: ежедневный запуск в 10:35 МСК, ручной запуск и reusable вызов после новой версии результатов.
- [ ] Ключ с резервной копией вне репозитория и secret; приватный репозиторий принимает только encrypted файлы.
- [ ] Независимое ревью, unit-тесты, первый реальный backup+restore прогон на GitHub; SHA-256 опубликованного ciphertext.
- [ ] Инструкция расшифрования, восстановления в новый Supabase и перечень оставшихся платформенных настроек.

## Review Focus

- Ошибка восстановления не считается успешным бэкапом; чувствительный stderr остаётся в приватной временной папке.
- Изменение/неверный ключ блокируют расшифрование до исполнения SQL.
- Исходный DB URL никогда не используется как цель восстановления.
- Сравнение включает auth.users, auth.identities, профили, прогнозы, результаты и scores.
- Ключ можно восстановить независимо от GitHub Secrets: файл на компьютере нужно отдельно сохранить владельцу.

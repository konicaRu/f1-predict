## 1. Зачем и что считаем успехом

Узнать, сколько одновременных пользователей выдерживает сервис (ступени **10 → 20 → 50 → 100 → 200**)
и где первое узкое место: тормозит, зависает или отдаёт ошибки.

Реальный профиль: сейчас в лиге около 5 человек, растём до 20–30. Пик — вечер дедлайна (четверг): в чат
приходит напоминание, все за пару минут жмут «Сделать прогноз» и сохраняют прогноз. **200 — запас на
рост, а не требование**; цель — знать границу и не удивиться ей.

Предварительные критерии (уточним по итогам первых замеров):

| Операция | p95 | Ошибки |
|---|---|---|
| Чтение (календарь, прогноз, зачёт, результаты) | < 1 с | < 1 % |
| Сохранение прогноза | < 2 с | < 1 % |
| Вход из Telegram (`telegram-auth`) | < 3 с | < 1 % |
| Любые 5xx / зависания дольше 10 с | нет | — |

## 2. Что нагружаем, а что нет

| Компонент | Нагружаем? | Почему / как |
|---|---|---|
| GitHub Pages (статика сайта) | **Нет** | CDN, против правил GitHub; мощность не узкое место (≈135 КБ на заход, лимит 100 ГБ/мес). Только лёгкие замеры веса, TTFB и загрузки из разных мест (S0) |
| Supabase REST (PostgREST + RLS) | Да | Календарь, прогноз, зачёт, результаты |
| Сохранение прогноза | Да, **в тестовом проекте** | upsert + триггер `validate_prediction` + триггер уведомления |
| Edge Function `telegram-auth` | Да | Самая тяжёлая: несколько обращений к Auth на каждое открытие; реальный пик «все нажали кнопку» |
| Вход по паролю (Auth) | Малым объёмом | Лимиты Auth по IP (значения уточнить в панели/документации) исказят результат |
| `admin-notify`, Gemini, Telegram | **Нет** | Спам админу в Telegram, квоты Gemini. В тестовом проекте не деплоить |
| `watchdog`, `pg_cron`, GitHub Actions | Нет | Не часть пользовательского пути |

## 3. Среда: отдельный проект Supabase (staging), прод не трогаем

Причина: тест создаст сотни прогнозов и пользователей и, главное, каждый прогон прогноза дёргает
`admin-notify` → сообщения админу и запросы к Gemini. Плюс нельзя мешать настоящим игрокам в дедлайн.

**Ловушки, которые надо обезвредить до первого запуска**
1. **`0023_admin_notify.sql` зашивает адрес функции и ключ ПРОДА.** В тестовой копии триггер
   `notify_admin_event()` либо не создавать, либо заменить URL на тестовый проект. Иначе нагрузочный
   тест начнёт слать боевой функции события.
2. **`0028_watchdog.sql` — `cron.schedule` смотрит на прод.** Не применять к тестовому проекту.
3. **`scripts/db/runner.js rebuild` СНОСИТ ВСЕ ТАБЛИЦЫ** и читает `SUPABASE_DB_URL` из корневого `.env`
   (это прод). Запуск против не того проекта = потеря боевых данных. Перед использованием: отдельная
   переменная для тестового проекта, печать ref проекта и обязательная сверка с тестовым; резервная копия
   (`node scripts/db/backup.js`) перед первым касанием раннера.
4. **Секреты в тестовом проекте:** для `telegram-auth` — **фейковый** `TELEGRAM_BOT_TOKEN` (им же
   подписываем синтетический `initData`); `TELEGRAM_*` боевые и ключ Gemini — **не задавать**.
5. **Данные:** ~200 синтетических пользователей (`loadtest+N@example.invalid`), пилоты, одна открытая
   гонка с пулом. После тестов проект можно удалить целиком.

## 4. Инструмент и откуда запускать

**k6** (бесплатный, сценарии на JavaScript, ступени нагрузки, перцентили из коробки, есть `k6/crypto`
для подписи `initData`). Docker на этой машине не работает — ставим бинарь для Windows. Скрипты — в
`scripts/loadtest/`.

Откуда запускать (**решить**):
- с машины разработчика — для разведки на 10–50; у машины свои особенности сети (VPN, WPAD, сообщения
  >8 КБ к пулеру Postgres не проходят), они могут исказить цифры;
- из облака (k6 Cloud или временный раннер) — для 100–200, чтобы не упереться в свой канал.

Лимиты Auth по IP обходим так: токены пользователей создаём заранее администратором, а сам вход по
паролю измеряем отдельным небольшим сценарием.

## 5. Сценарии

Каждая ступень — разгон, удержание 2–3 минуты, пауза. Между действиями «думает» 1–5 с.

| № | Сценарий | Что делает виртуальный пользователь |
|---|---|---|
| S0 | Статика | Не нагрузка: замер веса, TTFB, кеша, загрузки из разных мест (WebPageTest/Lighthouse); проверка блокирующего скрипта Telegram |
| S1 | Чтение | Календарь (гонки + «мои прогнозы») → страница прогноза (гонка с пулом, мой прогноз, список проголосовавших) → зачёт → результаты |
| S2 | Вечер дедлайна | N пользователей за ~5 минут сохраняют прогноз (1–3 раза каждый, повторы — upsert) |
| S3 | Вход из Telegram | N одновременных вызовов `telegram-auth` с подписанным `initData`: новые пользователи и уже привязанные |
| S4 | Вход по паролю | Малым объёмом (до лимитов Auth), оценить время ответа |
| S5 | Смесь | 70 % чтение, 20 % сохранение, 10 % входы — ступени 10/20/50/100/200 |

## 9. Вопросы и предложения (ждут твоего решения)

Предложения Claude от 2026-10-14. **Пока не приняты:** пользователь сказал «впиши, но пока ничего не
делай» — работы не начаты.

1. **Где тестировать → отдельный проект Supabase.** Безопасность важнее удобства: на проде каждый
   прогон прогноза слал бы админу сообщения и тратил квоты Gemini, а в вечер дедлайна мешал бы
   настоящим игрокам. Второй бесплатный проект ничего не стоит, потом удаляется целиком. Чтение на
   проде — опция на потом, только в тихие часы.
2. **Откуда запускать → в два этапа.** Сначала с компьютера разработчика, ступени 10–50 (отладка
   скриптов; искажения от VPN там не страшны). Для 100 и 200 — машина с нормальным каналом (облако или
   временный раннер); какая именно — после уточнения правил Supabase для нагрузочных тестов и бесплатных
   лимитов k6 Cloud (это нужно выяснить до этого этапа).
3. **Приоритет сценариев → S3, S2, S1, потом S5.**
   - S3 (вход из Telegram) первым: самый тяжёлый и совпадает с реальным пиком «все нажали кнопку»;
   - S2 (вечер дедлайна): самая важная для игры операция;
   - S1 (чтение): простые запросы, вероятно, выдержат;
   - S5 (смесь) последним, когда отдельные части измерены.
4. **Скрипт Telegram в `index.html` → чинить ДО нагрузочных тестов.** Самая дешёвая и реальная причина
   «зависает»: страница не отрисуется, пока не скачается сторонний скрипт, и от нагрузки это не
   зависит. Правка небольшая; замеряем до и после (S0); проверять нужно с телефона внутри Telegram,
   чтобы не сломать вход из Telegram.

**Предлагаемый порядок:** (1) скрипт Telegram + замеры S0, без инфраструктуры → (2) тестовый проект и
защита `rebuild` → (3) S3, S2, S1, S5 по ступеням.

## 10. Риски

- Бесплатные лимиты Supabase (трафик, вызовы функций, размер БД) — тест может их выработать; следить по
  панели, при необходимости останавливать.
- Промах проектом при `rebuild` — самый дорогой риск, см. раздел 3, пункт 3.
- Тестовая нагрузка с одного IP упирается в защиту от перебора (Auth) — заранее выдаём токены.
- Бесплатный тестовый проект засыпает через 7 дней без активности: запускать сразу после подготовки.

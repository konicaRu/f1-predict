# Экспорт в Google Sheets

Ручной бэкап прогнозов/результатов/очков лиги в Google-таблицу. Каждый запуск полностью
перезаписывает три вкладки актуальным снэпшотом из Supabase. Без автосинка (это отдельная
задача на будущее) — запускается по требованию.

## Разовая настройка

1. Открыть [Google Cloud Console](https://console.cloud.google.com/) → создать новый проект
   (или выбрать существующий).
2. В проекте: **APIs & Services → Library** → найти «Google Sheets API» → **Enable**.
3. **APIs & Services → Credentials → Create Credentials → Service Account**.
   Имя — любое (например `f1-predict-export`), роль на уровне проекта не нужна — доступ дадим
   точечно через шаринг конкретной таблицы (шаг 7). На экранах «Grant this service account
   access to project» и «Grant users access to this service account» ничего не выбирать и не
   заполнять — просто Continue/Done.
4. Открыть созданный сервис-аккаунт → вкладка **Keys → Add Key → Create new key → JSON**.
   Скачается файл ключа.
5. Положить скачанный файл в `scripts/export/service-account.json` (путь уже в `.gitignore`,
   в git не попадёт).
6. Открыть скачанный JSON, скопировать поле `client_email`
   (вид: `имя@проект.iam.gserviceaccount.com`).
7. Создать пустую Google-таблицу ([sheets.new](https://sheets.new)) → **Настройки доступа** →
   расшарить на email из шага 6 с правом **Редактор**.
8. Скопировать ID таблицы из её URL: `https://docs.google.com/spreadsheets/d/`**`ЭТОТ_ID`**`/edit`.
9. В корневом `.env` (НЕ `.env.example`) добавить (см. шаблон в `.env.example`):
   ```
   GOOGLE_SHEET_ID=<id из шага 8>
   GOOGLE_SERVICE_ACCOUNT_KEY_PATH=scripts/export/service-account.json
   ```

## Запуск

```bash
cd scripts/export
npm install   # один раз
npm run export
```

Скрипт сам создаст вкладки «Прогнозы», «Результаты», «Очки» (если их ещё нет в таблице),
полностью перезапишет их текущими данными и напечатает счётчики строк, например:

```
Прогнозы: 4 строк | Результаты: 1 строк | Очки: 4 строк
```

Это и есть проверка успешного запуска — отдельного verify-скрипта нет (низкий риск: только
чтение из Supabase и запись наружу, схема БД не меняется).

Если скрипт падает с ошибкой доступа (permission denied) — скорее всего таблица не расшарена
на email сервис-аккаунта из шага 6/7, или расшарена не на тот email. Проверить это в первую
очередь.

## Версионный резерв игрового архива

Старый `npm run export` — человекочитаемый отчёт с перезаписью вкладок. Он не запускается
автоматически и не заменяет резервные снимки.

Новый запуск из корня: `node scripts/export/snapshot.js` (или `npm run backup` в этой папке).
Создаёт **новый** лист `Архив <дата-время> UTC <суффикс>` в настроенной Google-таблице.
Старые снимки и вкладки отчёта не меняются и не удаляются. Время в названии листа — UTC,
ежедневное расписание ниже указано по МСК.

В копии семь таблиц с исходными ID и JSON: users, drivers, races, race_driver_pool, predictions,
results, result_changes. Manifest содержит время, git-коммит, миграции, количество строк и SHA-256.
По умолчанию БД читается в одной read-only repeatable-read транзакции.
После записи скрипт читает данные обратно и сверяет их. Только прошедший проверку лист получает
`COMPLETE` в B1. `PREPARING` означает незавершённую копию, для восстановления её не использовать.
Для технических листов намеренно хранится исходный JSON, а не человекочитаемый отчёт.

Если локальный VPN обрывает постоянное соединение, можно загрузить уже проверенную полную
локальную копию без auth-таблиц: `node scripts/export/snapshot.js from-backup "<папка копии>"`.
Проверяются manifest, все семь таблиц и SHA-256; источник помечается `verified-local-backup`.
Такой импорт наследует согласованность исходной локальной копии, не создаёт новый атомарный срез БД.

Скачать и проверить снимок:

```
node scripts/export/snapshot.js download "<название листа Архив ...>" "<новая приватная папка вне репозитория>"
```

Инструкции восстановления: [ARCHIVE-RESTORE.md](ARCHIVE-RESTORE.md).
Это резерв игрового архива, **без auth.users/auth.identities, паролей, секретов и Edge Functions**.
Для полной потери проекта нужен также полный приватный резерв авторизации и конфигурации.
Восстановление в рабочую базу автоматически не запускается.

### Ежедневное задание GitHub Actions

`.github/workflows/archive-backup.yml`: ежедневно в **10:15 МСК** (07:15 UTC), плюс ручной
`workflow_dispatch`. GitHub может задержать расписание; это время запроса запуска, не гарантия минуты.
Задания сериализованы, лимит одного прогона — 15 минут. Копия пишется только в Google Sheets,
публичные Actions artifacts не создаются. Ключ удаляется с runner после завершения.

Нужные repository secrets:

- `SUPABASE_DB_URL` — существующая строка БД.
- `GOOGLE_SHEET_ID` — существующая таблица, доступная сервисному аккаунту.
- `GOOGLE_SERVICE_ACCOUNT_JSON` — содержимое JSON-ключа этого аккаунта.

CLI поддерживает эти значения из `process.env`; при локальном запуске читает прежний `.env`.
Не сохранять ключ или архивы в git. Политика хранения первой версии — не удалять снимки;
при росте нужно контролировать лимит Google Sheets и отдельно согласовать ротацию.
Неудачный прогон виден красным в Actions; Telegram-уведомления эта задача не отправляет.

Проверки: `npm test` в `scripts/export` и `node --test scripts/db/restore-json.test.js` из корня.

## Дополнительный резерв в приватном GitHub

Репозиторий: `konicaRu/f1-predict-archive` (приватный). Папка `archive/` содержит датированные
снимки тех же семи игровых таблиц, manifest, SHA-256 и инструкцию восстановления.
`archive/latest.json` указывает на последнюю версию. Auth и пароли сюда не копируются.

Reusable workflow `github-archive.yml` вызывается из `telegram-notify.yml` отдельным заданием
того же прогона после режимов `autoresults`/`results`, включая случай ошибки Telegram.
Это резерв после того, как автозабор получил и сохранил результат, а не live-подписка на финиш:
сам автозабор проверяет источники раз в два часа. Ручная правка в админке попадёт в резерв
при следующем прогоне results/autoresults либо ежедневной проверке в 10:25 МСК.

Отпечаток `results + result_changes` предотвращает дубли. После штрафов/пересмотра сохраняется
новая папка, старые версии остаются. Существующая копия проверяется перед пропуском дубля.
Сбой копирования/commit/push делает задание красным, успешная обработка гонки в БД не откатывается.

Runner получает отдельный SSH deploy key только к архивному репозиторию из секрета
`ARCHIVE_DEPLOY_KEY` основного проекта. Не переносить архив в публичный репозиторий приложения.
Вручную повторить: Actions → Private GitHub result archive → Run workflow.
Скачивание приватного репозитория даёт готовые JSON-копии; инструкции — в RESTORE.md внутри
выбранной папки. Восстановление требует тех же условий по auth и схеме, что и снимки Sheets.

# Резерв пользователей и учебное восстановление

## Что сохраняется

Зашифрованный PostgreSQL custom dump схем `auth`, `public`, `extensions`: пользователи,
исходные UUID, хеши паролей, identities, auth-таблицы, профили, Telegram-связи, прогнозы,
результаты, функции, RLS, владельцы объектов и GRANT/ACL. Вместе с dump сохраняется manifest:
git-коммит, список необходимых ролей, SHA-256 dump и отпечатки/счётчики таблиц и scores.
Оригинальные пароли узнать из хешей нельзя; данные входа сохраняются для переноса в Auth.

Дамп создаётся в согласованном PostgreSQL snapshot; чтение рабочей базы read-only.
Платформенные API keys, SMTP/OAuth/Auth settings, Realtime settings, файлы Storage, глобальные
секреты и развёртывание Edge Functions в этот dump не входят. Их нужно настроить отдельно
по коду проекта и сохранённым секретам. Глобальные DB роли/членство также проверяются отдельно
при переносе; новые Supabase-проекты уже содержат стандартные роли.

## Где копия и ключ

- Приватный GitHub: `konicaRu/f1-predict-archive`, папка `full/`.
- `*.enc.json` — только AES-256-GCM ciphertext с аутентифицированным форматом.
- `full/latest.json` — путь, SHA-256 зашифрованного файла и результат учебного восстановления.
- Ключ хранится в GitHub Secret `FULL_BACKUP_KEY`; независимая копия владельца:
  `C:/claude_code_projects/f1_predict_backups/recovery/full-backup.key`.

Сохранить файл ключа отдельно от компьютера, например в личном менеджере паролей или на
резервном носителе. Не коммитить ключ рядом с архивом и не публиковать в сообщениях.
Без ключа AES-GCM копию расшифровать нельзя. Ротация ключа требует сохранения старого ключа
для предыдущих версий; автоматическая ротация не выполняется.

## Когда запускается

Ежедневно 10:35 МСК, вручную через workflow `Encrypted users backup and restore rehearsal`,
а также после новой или исправленной версии результатов в приватном GitHub-архиве.
Регистрация пользователя между такими запусками попадёт в следующий полный резерв.
GitHub может задержать расписание. Старые копии автоматически не удаляются.

## Что проверяет задание

1. Расшифровывает именно записанный encrypted файл и проверяет SHA-256 dump.
2. Создаёт временный PostgreSQL-контейнер с `--network none`, без внешних портов.
3. Восстанавливает в новую пустую БД `f1_recovery`, сохраняя owners и ACL.
4. Сравнивает количество и отпечатки всех таблиц auth/public и представления scores
   с той же исходной версией PostgreSQL snapshot. Проверяет отсутствие потерянных связей
   прогноз → auth.users и доступ роли authenticated к прогнозам выбранного пользователя.
5. Удаляет контейнер вместе с анонимными томами. В workflow есть дополнительная always-cleanup.
6. Только после успеха публикует encrypted копию и отметку о проверке.

Никакие строки пользователей, хеши паролей и dump не печатаются в логах. Временные дампы
не загружаются как Actions artifacts. Проверка БД не является проверкой SMTP/OAuth/Telegram
входа на новом домене: эти платформенные настройки требуют отдельной проверки при переносе.

## Как получить dump при аварии

Скачать нужный encrypted файл из приватного репозитория и проверить его SHA-256 по latest.json
(для последнего снимка). При необходимости выбрать более старую версию по дате и Git-истории.
В PowerShell, без вывода значения ключа:

```powershell
$env:FULL_BACKUP_KEY = (Get-Content -LiteralPath 'C:/claude_code_projects/f1_predict_backups/recovery/full-backup.key' -Raw).Trim()
node scripts/export/full-backup.js decrypt '<скачанный файл.enc.json>' '<новая приватная папка вне репозитория>'
Remove-Item Env:FULL_BACKUP_KEY
```

В папке появятся `database.dump` и `manifest.json`. До исполнения SQL просмотреть состав:
`pg_restore --list database.dump` (PostgreSQL 17).

Для реального переноса создать отдельный новый проект/БД, установить нужные расширения,
проверить роли и owners. Убедиться, что целевой URL отличается от рабочего; отдельно сохранить
его текущее состояние. Поскольку в новом Supabase Auth уже есть системные таблицы, порядок
замены существующих auth/public объектов нужно проверить на этом целевом проекте до применения.
Никогда не направлять тестовое восстановление на рабочую базу лиги.

После восстановления: сверить auth.users/identities, UUID-связи, прогнозы и очки; настроить
Auth/SMTP/OAuth/redirect URLs, API keys, Edge Functions и секреты. Обновить адреса проекта
в настройках сайта и автоматических заданий; проверить вход участника и админа.
Активные сессии при смене проекта/JWT могут потребовать повторного входа.
